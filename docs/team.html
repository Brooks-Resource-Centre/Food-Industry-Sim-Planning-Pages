Team Guide

For the development team. Academics only need the planning form.

One Unity project, two builds, many scenarios.

  • PC browser build: Unity WebGL (WebGPU optional, experimental). First-person walk, mouse and keyboard, 2D clipboard panel. No WebXR.
  • Standalone VR build: Android (Quest-class headset). Hand-held clipboard, grab and point.
  • Pilot scenario: pest ingress and maintenance failings (open it in the form).

Workflow for every scenario

  1. Plan (academic). The academic completes the planning form and signs it off before building.
  2. Data. Use the form's Data file for the team button to get the fault JSON. Save it in StreamingAssets. A pilot example is in data/pest-maintenance.faults.json.
  3. Greybox. Block out the room with primitives. Check scale, sight lines and the walking route in both builds.
  4. Art pass. Swap in real models, textures and decals. Bake lighting.
  5. Interactions. Hook faults to the shared inspect, flag and classify system.
  6. Platform test. Run the browser and Quest builds against the budgets below.
  7. Pilot with students. Record time to find each fault and what was missed. Feed it back into the form (section 11).
  8. Review. Note the real effort and which assets can be reused for the next scenario.

What the team needs

The academic-facing checklist is on the Resources page. This is the technical side.

  • People: Unity developer, 3D / environment artist, someone to look after headsets, builds and web hosting.
  • Hardware: standalone VR headsets (Quest-class), a development PC with a capable GPU, a typical student PC for browser testing, web hosting for large static files.
  • Software: Unity LTS with WebGL and Android modules, XR Interaction Toolkit, Blender or equivalent, Git with large-file support.
  • Reusable assets: building shell, warehouse props, maintenance props, pest props, documents. Characters and equipment come with later scenarios.
  • Risks: browser build too large or slow, VR frame rate drops, scope creep in the environment.

Suggested Unity layout

Assets/
  Core/            shared, scenario-independent code
    Audit/         fault model, flagging, classification, scoring
    Input/         PC and VR input behind one interface (IAuditInput)
    UI/            clipboard panel (one UI, two presentations)
    Data/          JSON loader for fault files
  Scenarios/
    PestMaintenance/   scene, props, materials, scenario-only scripts
    <NextScenario>/
  SharedAssets/    reusable props (pallets, doors, pipes, PPE, signage)
  Platform/
    WebGL/         build settings, loading screen
    Quest/         XR rig, build settings
  StreamingAssets/ fault JSON files (editable without rebuilding)

Rules that keep it cheap to extend:

  • A scenario is a scene, a fault JSON and some props. Core code is not edited for a new scenario.
  • Anything inspectable carries a FaultTarget component pointing at a fault id from the JSON.
  • Gameplay code talks to IAuditInput, never to the device directly.
  • Keep shared props in SharedAssets so the next scenario starts with a library.

{
  "scenario": "pest-maintenance",
  "title": "...",
  "faults": [
    {
      "id": "F-01",
      "area": "loading bay",
      "description": "what the student sees",
      "hint": "...",
      "correctClassification": "critical | major | minor",
      "clauseRef": "TBC",
      "linkedRecords": ["record-id"],
      "learningNote": "why it matters"
    }
  ],
  "records": [
    { "id": "record-id", "title": "...", "location": "...", "shows": "..." }
  ],
  "assets": [
    { "name": "...", "type": "Room or building | Object | Damage or marking | Document or record | Person | Sound | Other",
      "where": "...", "faults": "1, 3", "reference": "Have photo | Have sample | Need help finding | Not needed", "notes": "..." }
  ]
}

The assets list is the build list. Check it against SharedAssets first and build only what is missing.

Unity version note

Use a Unity 6 LTS release if available to your team. Check the current WebGPU status in its release notes before relying on it. Treat WebGL2 as the safe target.

Publishing these pages on GitHub

This site is plain static files in the docs folder. In the GitHub repository go to Settings, Pages, choose the main branch and the /docs folder. The Word export loads one small library from a CDN, so the form needs an internet connection to create the document.
